= 하나의 실험에서 수행하는 통합 평가

이 모듈에서는 정확도와 성능을 함께 다룹니다. 모델을 대상으로 5개의 한국어 정확도 벤치마크와 GuideLLM 처리량 테스트를 실행하고, 모든 결과를 하나의 MLflow 실험에 기록한 후 나란히 비교합니다.

이 모듈을 완료하면 다음을 갖추게 됩니다:

* 릴리스 결정에 동일한 모델 버전의 정확도 및 성능 결과가 모두 필요한 이유에 대한 이해
* 하나의 MLflow 실험에 기록된 5개의 정확도 작업과 1개의 성능 작업
* 노트북과 MLflow에서 수행한 전체 결과 비교

== 통합 평가가 필요한 이유

모듈 3과 모듈 4에서는 작업마다 별도의 실험이 생성되었습니다. 이 방식은 한 번에 하나의 측면을 살펴볼 때는 적합하지만, 릴리스 결정을 위해서는 동일한 모델 버전의 모든 측면을 나란히 확인해야 합니다:

* *새 버전의 정확도가 충분한가?* 각 벤치마크의 정확도가 기준치를 충족해야 합니다.
* *새 버전의 속도가 충분한가?* 처리량과 지연 시간이 서비스 수준 목표(SLO)를 충족해야 합니다.
* *이전 버전보다 나은가?* 모든 버전에 대해 동일한 결과 세트가 있어야 비교할 수 있습니다.

하나의 평가 회차를 하나의 MLflow 실험에 기록하면 이러한 기록을 확보할 수 있습니다. 다음 모델 버전을 동일한 벤치마크와 설정으로 평가하면 두 회차를 직접 비교할 수 있습니다.

== 통합 평가의 동작 방식

노트북은 평가를 두 단계로 실행하며, 두 단계의 결과를 모두 `<model-name>-full-eval-<timestamp>` 형식의 이름을 가진 실험에 기록합니다:

[cols="1,2,3",options="header"]
|===
| 단계 | 작업 | 수행 내용

| *Phase A: 정확도*
| 5개의 Korean MCQ 작업: `click`, `haerae`, `kmmlu`, `kmmlu_hard`, `kobest_boolq`
| 5개 작업이 한 번에 제출되어 병렬로 실행되며, 각 작업은 `LIMIT` 개수만큼의 문항을 평가합니다.

| *Phase B: 성능*
| `throughput` 프로파일을 사용하는 1개의 GuideLLM 작업
| 모든 정확도 작업이 완료된 후 시작되므로, 성능 테스트 중에 정확도 작업이 모델에 부하를 더하지 않습니다. 모델이 수용할 수 있는 최대 속도로 최대 180초 또는 50개 요청까지 요청을 전송하여 최대 처리량을 측정합니다.
|===

모듈 3에서 확인한 것처럼 GuideLLM 작업은 메트릭을 MLflow에 직접 기록하지 않습니다. 따라서 노트북에는 GuideLLM 메트릭을 동일한 실험에 기록하는 단계가 포함되어 있어, 모든 결과를 한 곳에서 확인할 수 있습니다.

== 핵심 개념: 하나의 실험, 여러 작업

통합 평가의 모든 작업은 동일한 `ExperimentConfig` 이름을 사용합니다. 작업마다 서로 다른 프로바이더를 사용할 수 있지만, MLflow는 모든 실행(run)을 하나의 실험 아래에 그룹화합니다:

[source,python,subs=none]
----
EXPERIMENT_NAME = f"{MODEL_NAME}-full-eval-{ts}"

# Phase A: one accuracy job per benchmark, all in the same experiment
for bm in ["click", "haerae", "kmmlu", "kmmlu_hard", "kobest_boolq"]:
    client.jobs.submit(JobSubmissionRequest(
        name=f"unified-{bm}-{ts}",
        model=model,
        benchmarks=[BenchmarkConfig(
            id=bm,
            provider_id=KOREAN_PROVIDER_ID,
            parameters={"temperature": 0.0, "max_tokens": 1024, "limit": LIMIT},
        )],
        experiment=ExperimentConfig(name=EXPERIMENT_NAME),
    ))

# Phase B: a performance job in the same experiment
perf_request = JobSubmissionRequest(
    name=f"unified-perf-{MODEL_NAME}-{ts}",
    model=guidellm_model,
    benchmarks=[BenchmarkConfig(
        id="throughput",
        provider_id="guidellm",
        parameters={
            "profile": "throughput",
            "max_seconds": 180,
            "max_requests": 50,
            "data": "prompt_tokens=128,output_tokens=64",
            "request_type": "chat_completions",
        },
    )],
    experiment=ExperimentConfig(name=EXPERIMENT_NAME),
)
----

하나의 작업의 `benchmarks` 목록에 여러 벤치마크를 포함할 수도 있습니다. 노트북의 *Evaluation 1*에서 이 패턴을 보여 주지만, 통합 평가에서는 각 벤치마크의 진행 상황을 개별적으로 확인할 수 있도록 벤치마크마다 하나의 작업을 제출합니다.

== 단계 5.1: 통합 벤치마크 노트북 열기

시작하기 전에 모듈 2부터 모듈 4까지 완료했는지 확인합니다. 이 모듈은 동일한 `.env` 파일, 모듈 2의 단계 2.5에서 수행한 `oc` 로그인, 모듈 2에서 등록한 Korean MCQ 프로바이더를 사용합니다.

*노트북 경로:* `{evalhub-lab-clone}/3_eval_hub_unified_benchmark/1_unified_benchmark.ipynb` ({evalhub-lab-repo}/blob/main/3_eval_hub_unified_benchmark/1_unified_benchmark.ipynb[GitHub에서 보기,window=_blank])

. JupyterLab 파일 브라우저에서 `rhoai-evalhub-lab` > `3_eval_hub_unified_benchmark` > `1_unified_benchmark.ipynb`를 엽니다.
. 맨 위부터 각 셀을 선택하고 *Shift+Enter*를 눌러 셀을 하나씩 실행합니다.

NOTE: 벤치마크당 문항 수는 `.env`의 `LIMIT` 값으로 결정되며 기본값은 `5`입니다. 모듈 4 이후에 `.env`를 변경했다면 첫 번째 셀을 실행하기 전에 노트북 커널을 다시 시작합니다(*Kernel* > *Restart Kernel*).

== 단계 5.2: 통합 평가 실행

아래 표를 사용하여 각 결과를 확인합니다. 노트북은 자체 단계 번호를 사용하며, 이는 이 모듈의 단계 번호와 다릅니다.

[cols="2,1,3",options="header"]
|===
| 노트북 셀 | 동작 | 예상 결과

| *Step 1: Configuration*
| 실행
| 네임스페이스, 모델 이름, 모델 엔드포인트, EvalHub URL, MLflow URI, `Sample Limit: 5`

| *Step 2: Initialize the EvalHub Client*
| 실행
| `Model auth secret 'model-api-key' ready`, `EvalHub client connected`, 모델 대상

| *Step 3: Discover Available Korean Benchmarks*
| 실행
| `Korean MCQ provider found (id=...)`와 한국어 벤치마크 목록

| *Evaluation 1: Multi-Benchmark Korean Evaluation* (셀 3개)
| 실행
| 첫 번째 셀은 헬퍼 함수를 정의합니다. 두 번째 셀은 `kmmlu`, `click`, `haerae`에 대한 다중 벤치마크 요청을 출력합니다. 세 번째 셀은 `Skipped - see Phase A below`를 출력하며, 작업은 제출되지 않습니다.

| *Evaluation 2: Sample Size Comparison* (셀 2개)
| 실행
| `2 jobs ready`와 `Skipped - see Phase A below`가 출력되며, 작업은 제출되지 않습니다.

| *Evaluation 3: Unified Evaluation*, Phase A 제출 셀
| 실행
| 통합 실험 이름(예: `redhataigemma-4-e4b-it-full-eval-1106-0845`)과 5개 벤치마크 각각의 작업 ID

| Phase A 대기 셀
| 실행
| 15초마다 5개 작업의 상태가 출력된 후 `All accuracy jobs finished!`와 각 벤치마크의 정확도

| *Phase B: GuideLLM Performance*
| 실행
| GuideLLM 작업 ID, 이어서 `GuideLLM job completed!`, 성능 메트릭, `All results tracked in MLflow experiment: ...`

| *Log GuideLLM Metrics to MLflow (Manual)*
| 실행
| 실행 이름 및 메트릭과 함께 `GuideLLM metrics logged to MLflow experiment: ...`

| *Step 4: Results Comparison* (셀 2개)
| 실행
| 네임스페이스에서 완료된 모든 작업의 메트릭 비교. 먼저 텍스트로, 이어서 표로 출력됩니다.

| *Step 5: MLflow Results*
| 읽기
| MLflow UI에 대한 배경 설명이며, 실행할 코드는 없습니다.

| *Step 6: Export Results* (셀 2개)
| 실행
| Markdown 비교 표, 이어서 완료된 각 작업에 대해 `Saved: ../results/<model-name>/...json`
|===

Phase A 제출 셀이 출력한 통합 실험 이름을 복사합니다. 이 이름은 단계 5.3에서 MLflow의 결과를 찾을 때 사용합니다.

NOTE: 비교 및 내보내기 셀에는 네임스페이스에서 완료된 모든 작업이 포함되므로 모듈 2부터 모듈 4까지의 작업도 함께 표시됩니다. 통합 평가 작업은 이름이 `unified-`로 시작하는 작업입니다.

== 단계 5.3: MLflow에서 통합 실험 확인

. {productname-short} 대시보드의 왼쪽 탐색 메뉴에서 *Develop & train*을 펼치고 *Experiments*를 클릭합니다.
. *Project* 드롭다운에서 본인의 프로젝트를 선택합니다.
. 노트북이 출력한 `<model-name>-full-eval-<timestamp>` 이름의 실험을 클릭합니다.
. 실험 페이지 상단에서 보기를 *GenAI*에서 *Model training*으로 전환합니다. 이 실험에는 6개 작업의 실행이 모두 포함되어 있습니다:
+
* 각 정확도 작업에 대해, 작업이 제출될 때 EvalHub가 생성하는 `unified-<benchmark>-<timestamp>` 이름의 실행과, 정확도 메트릭이 포함된 작업 ID에 `_0` 접미사가 붙은 이름의 실행이 있습니다.
* GuideLLM 작업에 대해, 평가 카드가 포함된 `unified-perf-<model-name>-<timestamp>` 이름의 실행과, 노트북이 기록한 성능 메트릭이 포함된 `guidellm-unified-perf-...` 이름의 실행이 있습니다.
+
image::unified/img-unified-mlflow-model-training-runs.png[5개 정확도 작업과 GuideLLM 작업의 실행 목록을 보여 주는 full-eval 실험의 Model training 보기]
+
작업 ID 이름을 가진 실행은 완료 상태와 짧은 소요 시간을 표시하며, 메트릭이 포함된 정확도 실행입니다. `unified-...` 실행은 *Running* 상태로 유지됩니다.

. 결과를 비교하려면 실행 목록 위의 차트 아이콘을 클릭합니다. MLflow는 메트릭마다 하나의 차트를 표시하며, 각 실행은 서로 다른 색상의 막대로 표시됩니다:
+
* `overall_accuracy`와 `overall_score`로 5개 벤치마크를 한눈에 비교할 수 있습니다.
* `category_accuracy.<category>` 차트는 샘플링된 문항이 속한 각 카테고리의 정확도를 보여 줍니다.
* 노트북이 GuideLLM 처리량 및 지연 시간 메트릭을 기록하면, 해당 메트릭이 추가 차트로 표시됩니다.
+
실행 목록에서 실행 옆의 눈 아이콘을 클릭하면 해당 실행을 차트에서 숨기거나 표시할 수 있습니다.
+
image::unified/img-unified-mlflow-charts.png[정확도 실행 간 카테고리 정확도, 전체 정확도, 전체 점수를 비교하는 full-eval 실험의 차트 보기]

TIP: 나중에 다른 모델이나 새 버전을 평가할 때는 벤치마크 ID, `LIMIT`, GuideLLM 프로파일을 동일하게 유지합니다. MLflow 비교는 평가 설정이 일치할 때만 의미가 있습니다.
