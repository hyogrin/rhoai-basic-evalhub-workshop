= GuideLLM 성능 벤치마크

이 모듈에서는 모델이 요청을 얼마나 빠르게 처리하는지 측정합니다. LLM 추론 서버용 부하 테스트 도구인 *GuideLLM*을 모듈 2에서 사용한 것과 동일한 EvalHub 클라이언트를 통해 실행하고, MLflow에서 결과를 비교합니다.

이 모듈을 완료하면 다음을 갖추게 됩니다:

* 주요 추론 성능 지표와 부하 프로파일에 대한 이해
* EvalHub를 통해 실행한 세 가지 GuideLLM 성능 작업: 빠른 기준선, 속도 스윕, 일정 부하 테스트
* MLflow에 기록된 각 작업의 성능 지표

== 성능을 측정하는 이유

정확하게 답변하는 모델이라도 응답이 너무 느리거나 예상 사용자 수를 감당하지 못하면 운영 환경에 적합하지 않습니다. 정확도와 성능은 서로 독립적인 출시 기준입니다:

* *사용자 경험*은 첫 단어가 얼마나 빨리 나타나고 나머지 답변이 얼마나 매끄럽게 스트리밍되는지에 따라 달라집니다.
* *용량 계획*은 지연 시간이 저하되기 전까지 배포가 처리할 수 있는 요청 수에 따라 달라집니다.
* *회귀 감지*는 반복 가능한 기준선에 따라 달라집니다. 이를 통해 새 모델 버전, 런타임 설정 또는 하드웨어 프로파일이 서빙을 더 빠르게 했는지 느리게 했는지 판단할 수 있습니다.

GuideLLM은 제어된 속도로 모델 엔드포인트에 합성 요청을 보내고 그 결과를 기록하여 이러한 질문에 답합니다.

== GuideLLM이 측정하는 항목

[cols="1,3",options="header"]
|===
| 지표 | 의미

| *첫 토큰까지의 시간(Time to First Token, TTFT)*
| 사용자가 답변의 첫 토큰을 받기까지 기다리는 시간입니다. 사용자가 가장 크게 체감하는 지연 시간입니다.

| *토큰 간 지연 시간(Inter-Token Latency, ITL)*
| 연속된 출력 토큰 사이의 시간입니다. ITL이 낮을수록 스트리밍이 더 매끄럽습니다.

| *종단 간 지연 시간(End-to-End Latency, E2E)*
| 요청을 보낸 시점부터 전체 응답을 받을 때까지의 총 시간입니다.

| *처리량*
| 배포가 유지할 수 있는 초당 출력 토큰 수 또는 초당 요청 수입니다.
|===

지연 시간 지표는 일반적으로 p50(중앙값)과 p99(가장 느린 1%의 요청) 같은 백분위수로 보고됩니다.

== 이 모듈에서 사용하는 부하 프로파일

*프로파일*은 GuideLLM이 부하를 생성하는 방식을 정의합니다. 이 모듈에서는 세 개의 작업에 걸쳐 두 가지 프로파일을 사용합니다:

[cols="1,1,3",options="header"]
|===
| 작업 | 프로파일 | 목적

| *빠른 기준선*
| `constant`
| 초당 2개의 요청을 120초 동안 보내 첫 번째 지연 시간 기준선을 확보합니다.

| *속도 스윕*
| `sweep`
| 한 번에 하나의 요청부터 최대 처리량까지 각 120초씩 10단계를 실행하여, 지연 시간이 저하되기 시작하는 속도를 파악합니다. 약 20분이 소요되는 가장 긴 작업입니다.

| *일정 부하*
| `constant`
| 짧은 워밍업 후 고정된 속도를 유지하여 안정 상태의 성능을 측정합니다. 실제로는 스윕 결과를 바탕으로 속도를 설정합니다.
|===

각 요청은 256개의 프롬프트 토큰과 128개의 출력 토큰으로 구성된 합성 데이터를 사용하므로 실행(run) 간에 결과를 비교할 수 있습니다. GuideLLM은 `throughput`, `concurrent`, `poisson` 등 다른 프로파일도 지원하며, 워크숍 이후에 살펴볼 수 있습니다.

== 핵심 개념: 동일한 클라이언트, 다른 프로바이더

모듈 2에서는 Korean MCQ 프로바이더에 정확도 작업을 제출했습니다. 성능 작업도 동일한 클라이언트와 동일한 `JobSubmissionRequest` 구조를 사용합니다. 프로바이더와 매개변수만 달라집니다:

[source,python,subs=none]
----
quick_request = JobSubmissionRequest(
    name=f"guidellm-quick-{MODEL_NAME}-{ts}",
    description=f"Quick performance baseline for {MODEL_NAME}",
    tags=["performance", "guidellm", MODEL_NAME],
    model=model,                         # model endpoint and API key Secret
    benchmarks=[
        BenchmarkConfig(
            id="constant",               # GuideLLM profile
            provider_id="guidellm",      # built-in EvalHub provider
            parameters={
                "profile": "constant",
                "rate": 2,               # requests per second
                "max_seconds": 120,      # test duration
                "data": "prompt_tokens=256,output_tokens=128",
                "request_type": "chat_completions",
            },
        )
    ],
    experiment=ExperimentConfig(name=f"guidellm-quick-{MODEL_NAME}-{ts}"),
)

quick_job = client.jobs.submit(quick_request)
----

EvalHub는 정확도 스모크 테스트와 마찬가지로 GuideLLM을 네임스페이스의 작업으로 실행하고, 진행 상황을 보고하며, 지표를 MLflow에 기록합니다.

시작하기 전에 모듈 2를 완료했는지 확인합니다. 이 모듈은 동일한 `.env` 파일과 모듈 2의 단계 2.5에서 수행한 `oc` 로그인을 사용합니다.

*노트북 경로:* `{evalhub-lab-clone}/1_eval_hub_guidellm_benchmark/1_guidellm_benchmark.ipynb` ({evalhub-lab-repo}/blob/main/1_eval_hub_guidellm_benchmark/1_guidellm_benchmark.ipynb[GitHub에서 보기,window=_blank])

. JupyterLab 파일 브라우저에서 `rhoai-evalhub-lab` > `1_eval_hub_guidellm_benchmark` > `1_guidellm_benchmark.ipynb`를 엽니다.
. 맨 위부터 각 셀을 선택하고 *Shift+Enter*를 눌러 셀을 하나씩 실행합니다.

NOTE: 모듈 2 이후에 `.env`를 변경한 경우, 새 값이 로드되도록 첫 번째 셀을 실행하기 전에 노트북 커널을 다시 시작합니다(*Kernel* > *Restart Kernel*).

== 단계 3.2: 성능 작업 실행

아래 표를 사용하여 각 결과를 확인합니다. 노트북은 자체 단계 번호를 사용하며, 이 모듈의 단계 번호와 다릅니다.

[cols="2,1,3,1",options="header"]
|===
| 노트북 셀 | 동작 | 예상 결과 | 예상 소요 시간

| *Step 1: Configuration*
| 실행
| 네임스페이스, 모델 이름, `/v1`로 끝나는 GuideLLM 엔드포인트, `Using external EvalHub URL: ...`
| 수 초

| *Step 2: Initialize EvalHub Client*
| 실행
| `Model auth secret 'model-api-key' ready`, `GuideLLM provider registered: True`, GuideLLM 벤치마크 목록
| 수 초

| *Step 3: Quick Performance Baseline* (셀 2개)
| 실행
| 상태가 `pending`인 작업 ID, 작업이 `running`인 동안의 경과 시간, 이어서 `Job completed!`와 다섯 가지 성능 지표
| 약 2~3분

| *Step 4: Rate Sweep Test* (셀 2개)
| 실행
| 스윕 작업 ID, 이어서 `Job completed!`와 스윕 지표
| 약 20분

| *Step 5: Constant Load Test* (셀 2개)
| 실행
| 일정 부하 작업 ID, 이어서 `Job completed!`와 안정 상태 지표
| 약 2~3분
|===

각 모니터링 셀은 10초마다 작업 상태를 확인하고 경과 시간을 출력합니다. 빠른 기준선 작업과 일정 부하 작업은 각각 약 2~3분 동안 실행됩니다. 부하 테스트 자체는 120초 동안 진행되며, 작업 시작과 결과 보고에 몇 초가 추가됩니다. 속도 스윕은 각 120초씩 10단계를 실행하므로 약 20분 동안 실행됩니다. 다음 셀을 실행하기 전에 각 셀이 완료될 때까지 기다립니다. 셀이 대기 중인 동안에도 작업은 네임스페이스에서 계속 실행됩니다. 작업을 동시에 실행하면 결과가 왜곡되므로 작업을 하나씩 순서대로 실행합니다.

TIP: 스윕 모니터링 셀은 약 20분 후 대기를 중단하며, 이는 스윕의 실행 시간과 비슷합니다. 셀이 `Job completed!`를 출력하기 전에 중단되더라도 작업은 계속 실행 중입니다. 위의 제출 셀이 아닌 모니터링 셀만 다시 실행하면 동일한 작업을 기다린 후 지표를 출력합니다.

NOTE: *Step 5: Constant Load Test*를 시작하기 전에 스윕이 완료될 때까지 기다립니다. 다른 셀이 실행 중일 때 셀을 실행하면 Jupyter는 해당 셀을 `[*]`로 표시하여 대기열에 넣고, 실행 중인 셀이 완료된 후에 시작합니다. 일정 부하 테스트를 일찍 시작하기 위해 스윕 모니터링 셀을 중단하지 마십시오. 두 테스트가 동시에 같은 모델에 부하를 보내 서로의 결과를 왜곡하게 됩니다.

NOTE: 부하 테스트는 짧은 시간에 많은 요청을 보냅니다. 모델 API 키의 토큰 속도 제한이 낮으면 일부 요청이 HTTP `429`로 제한될 수 있으며, 이 경우 지연 시간 결과에 해당 제한이 반영됩니다. 지표에서 실패한 요청이 많이 보이면 강사에게 구독의 속도 제한을 문의하십시오.

=== 빠른 기준선 결과

빠른 기준선이 완료되면 모니터링 셀이 작업의 지표를 출력합니다:

.성능 지표와 함께 완료된 빠른 기준선
image::guidellm/img-guidellm-quick-baseline-completed.png[성능 지표와 함께 완료된 GuideLLM 빠른 기준선 작업을 보여 주는 노트북 출력]

[cols="1,3",options="header"]
|===
| 출력 지표 | 의미

| `mean_ttft_ms`
| 첫 토큰까지의 평균 시간(밀리초)

| `mean_itl_ms`
| 평균 토큰 간 지연 시간(밀리초)

| `output_tokens_per_second`
| 모든 요청에 걸쳐 초당 생성된 출력 토큰 수

| `prompt_tokens_per_second`
| 모든 요청에 걸쳐 초당 처리된 프롬프트 토큰 수

| `requests_per_second`
| 초당 완료된 요청 수입니다. 목표 속도가 2일 때 값이 2에 가까우면 배포가 부하를 감당했음을 의미합니다.
|===

NOTE: `MLflow Run: None`은 정상입니다. 현재 GuideLLM 작업은 지표를 MLflow 실행에 기록하지 않으므로, 성능 결과는 노트북 출력에서 확인합니다.

=== 속도 스윕 결과

약 20분 후 스윕이 완료되면 모니터링 셀이 `Job completed!`와 스윕의 지표를 출력합니다:

.보고된 지표와 함께 완료된 속도 스윕
image::guidellm/img-guidellm-sweep-completed.png[지표와 함께 완료된 GuideLLM 속도 스윕 작업을 보여 주는 노트북 출력]

스윕의 `requests_per_second`와 처리량 값은 빠른 기준선보다 훨씬 낮습니다. 이는 정상입니다. 스윕에 대해 반환되는 지표는 10단계 전체가 아니라 한 번에 하나의 요청을 보내는 첫 번째 단계를 요약한 것입니다. 이 예시에서 각 요청은 약 5.7초(TTFT와 토큰 간 지연 시간에 따른 128개 출력 토큰)가 소요되므로, 단일 스트림은 초당 약 0.17개의 요청을 완료합니다. 이 단계를 모델의 최상의 단일 사용자 지연 시간으로 활용합니다.

=== 일정 부하 결과

일정 부하 테스트가 완료되면 모니터링 셀이 `Job completed!`와 안정 상태 지표를 출력합니다:

.안정 상태 지표와 함께 완료된 일정 부하 테스트
image::guidellm/img-guidellm-constant-load-completed.png[안정 상태 지표와 함께 완료된 GuideLLM 일정 부하 작업을 보여 주는 노트북 출력]

일정 부하 테스트는 빠른 기준선과 동일한 속도와 시간을 사용하며, 결과에서 제외되는 짧은 워밍업이 추가됩니다. `requests_per_second`가 목표값 2에 가까우므로 배포가 이 부하를 유지한다는 것을 확인할 수 있습니다. TTFT와 토큰 간 지연 시간을 빠른 기준선과 비교하여 워밍업의 효과를 확인합니다.

== 단계 3.3: MLflow에서 성능 결과 확인

각 GuideLLM 작업은 작업 유형, 모델, 노트북의 *Step 3*을 실행한 시점의 타임스탬프로 이름이 지정된 자체 MLflow 실험을 생성합니다. 모듈 2의 정확도 실행과 달리 GuideLLM 실행은 지표 차트를 기록하지 않습니다. EvalHub는 각 실행에 첨부된 *평가 카드* 파일에 결과를 저장합니다.

. {productname-short} 대시보드의 왼쪽 탐색 메뉴에서 *Develop & train*을 펼치고 *Experiments*를 클릭합니다.
. *Project* 드롭다운에서 본인의 프로젝트를 선택합니다.
. 노트북을 끝까지 실행하면 목록에 세 개의 GuideLLM 실험이 모두 동일한 타임스탬프로 표시됩니다: `guidellm-quick-...`, `guidellm-sweep-...`, `guidellm-constant-...`. 모듈 2의 `korean-llm-evaluation` 실험도 함께 표시됩니다. GuideLLM 실험만 표시하려면 `guidellm`을 검색합니다.
+
image::guidellm/img-guidellm-experiments-list.png[세 개의 GuideLLM 실험과 korean-llm-evaluation 실험이 나열된 user3 프로젝트의 Experiments 페이지]

. `guidellm-quick-...` 실험을 클릭합니다. 실험 페이지 상단에서 보기를 *GenAI*에서 *Model training*으로 전환하여 해당 실행을 표시합니다.
+
image::guidellm/img-guidellm-mlflow-model-training-runs.png[실행이 나열된 Model training 보기의 GuideLLM quick 실험]
. 실행을 클릭하고 *Artifacts* 탭을 연 다음 `evaluation-card.json`을 선택합니다. 카드 상단의 `context` > `benchmarks`에는 프로파일, 속도, 시간, 토큰 크기 등 작업 매개변수가 표시됩니다. 아래로 스크롤하여 `results` 섹션의 `benchmarks` > `metrics`에서 성능 지표를 확인합니다.
+

NOTE: GuideLLM 실행은 작업이 완료된 후에도 *Running* 상태와 빈 지표 보기를 표시합니다. 이는 정상입니다. 지표는 `evaluation-card.json`과 노트북 출력에 있으며, 두 곳에는 같은 값이 표시됩니다.

스윕의 단일 사용자 지연 시간을 초당 2개 요청의 빠른 기준선 및 일정 부하 결과와 비교합니다. 이 예시에서 일정 부하 테스트의 TTFT(약 175ms)는 단일 사용자 TTFT(약 173ms)와 거의 같으므로, 배포가 개별 요청을 느리게 하지 않고 초당 2개의 요청을 처리합니다. 빠른 기준선의 더 높은 TTFT(약 199ms)는 워밍업 없이 시작한 테스트의 첫 요청들에서 비롯되며, 이 때문에 일정 부하 테스트에는 워밍업 단계가 추가되어 있습니다.

동일한 EvalHub 클라이언트로 한국어 객관식 벤치마크에서 모델의 정확도를 측정하려면 모듈 4로 진행합니다.
